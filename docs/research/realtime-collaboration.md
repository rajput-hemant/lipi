# Phase 5: real-time collaboration research

Research date: 2026-09-27. This checkout has no `data/lipi-discovery-plan/report.md` and no existing research directory, so this note records the implementation findings under `docs/research/`.

## Minimal implementation decisions

1. Use the official Hocuspocus v4 server and provider with the existing Node 22 baseline. Hocuspocus is the Yjs WebSocket provider, and its database extension accepts async fetch/store callbacks, so a small adapter can persist the binary Yjs state in a Lipi-prefixed Postgres table. Keep `@hocuspocus/server`, `@hocuspocus/provider`, and the database extension on matching v4 releases. [Hocuspocus overview](https://tiptap.dev/docs/hocuspocus/getting-started/overview), [v4 upgrade guide](https://tiptap.dev/docs/hocuspocus/getting-started/upgrade), [database extension](https://tiptap.dev/docs/hocuspocus/server/extensions/database)

2. Authenticate in `onAuthenticate`, before any room data is loaded. Pass the WebSocket request `Headers` to the existing Better Auth instance's `auth.api.getSession({ headers })`, parse and validate the room name as a document UUID, resolve its workspace membership, then check `document:read` or `document:write` with `lib/workspace/permissions`. Reject missing users, malformed or forged document IDs, deleted/missing documents, and non-members. Set `connection.readOnly = true` for viewers. Return only verified user identity in Hocuspocus context and refresh permissions on `onTokenSync` so an open room can respond to session or membership changes. The standalone Node process should construct the existing `createAuth` factory with the shared schema and server DB client; `lib/auth.ts`'s `getSession` helper depends on Next's `headers()` and React cache. [Hocuspocus authentication](https://tiptap.dev/docs/hocuspocus/guides/authentication), [Hocuspocus hooks](https://tiptap.dev/docs/hocuspocus/server/hooks), [Better Auth API](https://better-auth.com/docs/concepts/api)

3. Use the current Better Auth cookie only when the browser sends it to the realtime endpoint. Better Auth's cross-subdomain cookie option is currently disabled in `lib/auth/create-auth.ts`; Better Auth documents host-only cookies as the default. Keep the auth configuration stable across deployments. Route the WebSocket through the app's cookie-owning host, or issue a short-lived, room-scoped collaboration token from an authenticated Lipi endpoint and validate it in Hocuspocus. Do not accept a user ID or room permission from client-supplied query parameters. [Better Auth cookies](https://better-auth.com/docs/concepts/cookies), [Better Auth API](https://better-auth.com/docs/concepts/api)

4. Persist the complete Yjs document as binary in a new `lipi_*` table, keyed by document ID, with a cascading foreign key and updated timestamp. Implement the Hocuspocus database extension's `fetch` and `store` with the existing Postgres client. Its `fetch` callback returns the saved `Uint8Array` or `null`; `store` writes the exact Yjs state bytes. Model the payload as PostgreSQL `bytea` using Drizzle's native type and the existing Lipi table creator. Never reconstruct an established room from JSON on reconnect: Hocuspocus warns that re-creating a Y.Doc loses history and can duplicate content. Add an exactly-once bootstrap for existing `documents.content` only when no Yjs state exists. Use BlockNote's `blocksToYDoc` for that import and keep its fragment name fixed. [Hocuspocus database extension](https://tiptap.dev/docs/hocuspocus/server/extensions/database), [Hocuspocus persistence](https://tiptap.dev/docs/hocuspocus/guides/persistence), [BlockNote Yjs utilities](https://www.blocknotejs.org/docs/reference/editor/yjs-utilities), [Drizzle PostgreSQL column types](https://orm.drizzle.team/docs/column-types), [Drizzle multi-project schema](https://orm.drizzle.team/docs/goodies#multi-project-schema)

5. Make Yjs the sole editing source of truth. Remove the editor's direct debounced write of `documents.content`; retain that column as a derived JSON snapshot for existing Lipi readers by updating it from Hocuspocus persistence using the same BlockNote schema. The Yjs binary remains authoritative during reload, reconnect, and concurrent updates. Hocuspocus supports storing an additional JSON representation, and BlockNote supplies YDoc-to-block conversion utilities. [Hocuspocus persistence](https://tiptap.dev/docs/hocuspocus/guides/persistence), [BlockNote Yjs utilities](https://www.blocknotejs.org/docs/reference/editor/yjs-utilities)

6. Wire the Phase 4 editor through `withCollaboration` from `@blocknote/core/yjs`, using the Hocuspocus provider, the same named XML fragment on every client, and verified user name/color. BlockNote documents Yjs collaboration as its native multiplayer integration; `showCursorLabels: "activity"` supplies cursor labels. Stamp the awareness `user` field from authenticated Hocuspocus context in `beforeHandleAwareness` so a client cannot impersonate another collaborator. Read room awareness to render live cursors and selections. [BlockNote real-time collaboration](https://www.blocknotejs.org/docs/features/collaboration), [Hocuspocus awareness](https://tiptap.dev/docs/hocuspocus/guides/awareness), [Hocuspocus hooks](https://tiptap.dev/docs/hocuspocus/server/hooks)

7. Use a workspace room for navbar presence and sidebar invalidation, separate from each document's editor room. Each room must have its own strict workspace/document authorization. A server action remains the authority for page creation and rename, preserving its existing permission and quota checks; after success, send a small stateless workspace event that tells other clients to refresh their document tree from the authorized Lipi query. Do not use the event payload to apply page data. Hocuspocus supports stateless messages and providers can share one WebSocket across multiple rooms. [Hocuspocus stateless hooks](https://tiptap.dev/docs/hocuspocus/server/hooks), [provider configuration](https://tiptap.dev/docs/hocuspocus/provider/configuration), [provider events](https://tiptap.dev/docs/hocuspocus/provider/events)

## Repository observations

- Phase 4 currently initializes BlockNote from `documents.content` and debounces writes back to that column in `components/document-editor/document-block-editor.tsx`.
- `lib/workspace/permissions.ts` defines owner, editor, and viewer roles. Viewers have `document:read` but not `document:write`.
- Existing page mutations live in `lib/db/actions/document.ts`; retain those authorization and quota-aware paths for page structure instead of mutating the sidebar tree through collaborative editor content.
- Lipi-only schema uses `createTable` from `lib/db/table-creator.ts`, and the migration filter is Lipi-prefixed. The Yjs persistence table belongs there and should receive the next migration after the current highest migration.
- Current package versions include BlockNote `^0.55.0`, Better Auth `^1.6.23`, Drizzle ORM `^0.45.3`, and Node `>=22.11.0`. Yjs and Hocuspocus packages are not currently direct dependencies.

## Source notes and caveats

- Hocuspocus v4 hook payloads use standard `Headers`, and v4 requires Node.js 22+. The repository's declared Node floor satisfies that requirement. [Hocuspocus hooks](https://tiptap.dev/docs/hocuspocus/server/hooks), [Hocuspocus upgrade guide](https://tiptap.dev/docs/hocuspocus/getting-started/upgrade)
- The Hocuspocus generic database extension has no Postgres-specific adapter requirement; its documented contract is async byte fetch and store callbacks, which can use Lipi's existing Postgres/Drizzle setup. [Hocuspocus database extension](https://tiptap.dev/docs/hocuspocus/server/extensions/database)
- Cursor identity sent through Yjs awareness is client-writable by default; Hocuspocus v4's `beforeHandleAwareness` hook exposes decoded state for server rewriting. Use it to replace the claimed user identity with verified room context. [Hocuspocus awareness hook](https://tiptap.dev/docs/hocuspocus/server/hooks), [Hocuspocus awareness guide](https://tiptap.dev/docs/hocuspocus/guides/awareness)
- A separate realtime hostname will not receive the current host-only session cookie. The owner should select the concrete endpoint arrangement before deployment; this does not block implementing and testing the server's authorization boundary. [Better Auth cookies](https://better-auth.com/docs/concepts/cookies)
